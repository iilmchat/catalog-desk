## 1. Архитектура

```
браузер пользователя
 ├─ Пятёрочка: 5ka_export_* + 5ka_batch_enrichment_v16.user.js
 └─ Перекрёсток: pr_export_* + pr_batch_enrichment_v16.user.js
                   │
                   ▼ только видимый DOM
              JSON Export v2
                   │
                   ▼
 catalog_ui_server_v14.py :8767 ── import_5ka_catalog_v9.py
                   │                      │
                   └──────── SQLite ◄─────┘
                              │
                              ▼
                    ui_v14/ + локальный API
                              │
                         Excel / CSV
```

**Одиночное обновление V16:** интерфейс выпускает одноразовый токен, связанный с точным `(chain, sap_code, plu)`. Он действует 10 минут и принимается один раз. Отдельный импорт обновляет `product_details`, `product_detail_history`, `product_detail_imports` и `product_images`, не изменяя `enrichment_tasks`, `enrichment_task_events` или `enrichment_batch_states`.

**Принцип сбора:** bookmarklet/userscript читает только то, что уже отображено на открытой странице. Скрытые API магазина, чтение cookies и обход CAPTCHA не используются. CAPTCHA означает остановку и ручную проверку.

## 2. Сети и идентичность товара

Единый реестр находится в `catalog_config.py`:

| Сеть | chain | Домены | SAP по умолчанию |
| :--- | :--- | :--- | :--- |
| Пятёрочка | `5ka` | `5ka.ru` | `35XY` |
| Перекрёсток | `perekrestok` | `perekrestok.ru` | `XSEO` |

Естественный ключ товара: `(chain, sap_code, plu)`. Один и тот же PLU в двух сетях — две независимые записи. SAP описывает магазин/контекст доставки внутри сети и также входит в ключ.

Импорт каталога и подробных карточек проверяет:
- известность сети;
- допустимость SAP для сети;
- отсутствие смешения chain внутри одной выгрузки;
- домен исходной страницы и ссылок на карточки.

Несоответствие отклоняется до записи в БД.

## 3. Слои и ответственность

| Слой | Файлы | Ответственность |
| :--- | :--- | :--- |
| Реестр | `catalog_config.py` | домены, SAP, URL, source markers, папки и Referer |
| Сбор | `5ka_export_*`, `pr_export_*`, userscripts | видимый DOM → JSON с chain/SAP/PLU |
| Приём | `catalog_ui_server_v14.py` | валидация, загрузка файлов, пакетное обогащение |
| Импорт | `import_5ka_catalog_v9.py` | идемпотентный импорт, история цен, экспорт |
| Хранилище | SQLite | история цены/карточки, изображения, избранное, очереди |
| Представление | `ui_v14/` | каталог, карточки, поиск, аналитика и экспорт |

## 4. Схема данных

Основные таблицы, содержащие товары, используют `chain`:
- `products`, `product_categories`, `price_history`, `exports`;
- `product_details`, `product_detail_history`, `product_images`;
- `favorites`, `enrichment_tasks`, `enrichment_task_events`.

Ключи товара и связанных снимков расширены до `(chain, sap_code, plu)`. В миграции V9→V10 старые записи получают `chain='5ka'`. Для ссылок на товар применяется соответствующий составной внешний ключ. Миграция выполняется транзакционно, с копией базы перед запуском и проверкой `PRAGMA foreign_key_check`.

Состояние пакетного сбора хранится отдельно для каждой сети в `enrichment_batch_states`. Старое состояние V14 из одиночной таблицы переносится при запуске обновлённой схемы.

## 5. Потоки данных

1. **Каталог:** видимый DOM → JSON → валидация сети/SAP/URL → `products` и `price_history`.
2. **Карточка:** видимый DOM → JSON → `product_details`, снимок в `product_detail_history`, фото в `product_images`.
3. **Очередь:** неполные карточки → `enrichment_tasks` → браузерный пакет → повторный импорт.
4. **Качество:** `details_text` → восстановление состава/описания/БЖУ → индикатор полноты и противоречия.
5. **Экспорт:** SQLite → Excel/CSV с колонкой сети.

## 6. Планирование и автоматизация

`daily_runs` сейчас хранит **план ручной выгрузки** по сети и дате. Это не автоматический планировщик: сервер не открывает браузер и не инициирует DOM-сбор в фоне. Сбор требует пользовательского браузера и ручного решения CAPTCHA.

Реализованы журнал ошибок, бэкап базы по запросу, пакетный режим и локальный API `/api/v1/*`. Сервер слушает только loopback (`127.0.0.1`, `localhost` или `::1`). HTTP handler дополнительно проверяет loopback peer и Host; Origin допускается для локального интерфейса или явно разрешённых доменов Пятёрочки/Перекрёстка (userscript через GM_xmlhttpRequest). POST требует `application/json`, корректный Content-Length в пределах 32 MiB и JSON-объект UTF-8. Это не аутентификация; API не предназначен для публикации в LAN.

## 7. Качество извлечения и тестирование

Одиночный refresh использует DOM-only сбор и отдельный одноразовый token, затем отдельный серверный путь импорта. Проверка после V16.1.0 подтвердила работу на одной карточке каждой сети и отсутствие изменений batch-state.

Текущие ограничения парсинга Перекрёстка:
- `description` явно передаётся как `null`;
- `composition` извлекается только если соответствующий текст попал в `productText` и совпал с ожидаемым шаблоном;
- граница основной карточки зависит от распознавания заголовка рекомендаций, поэтому возможны лишние фрагменты в `details_text`.

CI проверяет Python-тесты, синтаксис userscript, LinkeDOM и Chromium smoke на offline fixtures. S23 добавляет `_catalog_meta.schema_version=2` с provenance для каждого captured-поля: логическое поле источника, URL, время снимка и метод (`visible_dom`, `payload` или `taxonomy`). Статусы `not_found` и `not_applicable` не получают фиктивную provenance. Legacy metadata schema v1 остаётся читаемой; отдельная миграция SQLite не нужна.

## 8. Ограничения

- Пользовательский интерфейс локальный; аутентификации нет.
- Пакетный режим последовательный: один товар за раз, задержка 12–60 секунд.
- Состав и БЖУ собираются только если показаны на странице; автоматический разбор состава эвристический.
- Фотографии рекомендаций не должны попадать в галерею товара.
- Цена относится к онлайн-каталогу для выбранного адреса доставки и может отличаться от цены на полке.
- `pandas/openpyxl` нужны только для табличного экспорта.
